# Asteron retention agent — end to end

Everything needed to run the retention/diagnosis agent live: the
Cloudflare Worker (pipeline stages 2-4 from PROJECT_HANDOFF.md §4), the
rule-based Detection stage (stage 1), a synthetic dataset to detect
against, and the dealer dashboard (stages 5-6 — human approval gate,
then simulated send). Stage 7 (feedback loop) is still open — see "Not
yet built" at the bottom.

## What's in here

```
src/
  index.js                Worker entry point — POST /diagnose, GET /health
  completeness_check.js   ESM port of reasoning-core's deterministic pre-check (logic unchanged)
  system_prompt.js        Literal prompt from system_prompt.md, as an importable string
  llm_client.js           Gemini 2.5 Flash primary, Groq llama-3.3-70b fallback
  validate.js             Structural + the 4 x_worker_side_validation_rules from output_schema.json
  playbook.json           Copied verbatim from reasoning-core
  output_schema.json      Copied verbatim from reasoning-core
data/
  build_dataset.mjs       Generates 24 curated synthetic customer records
  customers.json          ...the records themselves (generated — re-run the script to rebuild)
  flagged_customers.json  ...the subset Detection flags (generated by detect.mjs)
detection/
  detect.mjs               Stage 1: rule-based Detection, no AI (service overdue, no first-service
                            booked, app inactivity, warranty proximity)
.github/workflows/
  detect.yml               Nightly GitHub Action running detect.mjs, commits the flagged list if changed
dashboard/
  index.template.html      Dealer dashboard source (edit this one)
  build.mjs                Fills the template with real data from flagged_customers.json + playbook.json
  index.html               Generated output — deploy this to GitHub Pages
test/
  example_records.json     Same 3 synthetic records from reasoning-core
  local_test.mjs           Offline tests for completeness_check.js + validate.js — no API key needed
  dashboard_smoke_test.mjs Headless-DOM test: renders all 23 tickets, clicks through, checks error paths
  dashboard_flow_test.mjs  Headless-DOM test: full question -> answer -> diagnosis -> approve flow, mocked Worker
wrangler.toml
package.json
.dev.vars.example         Template for local secrets (never commit real keys)
```

## End-to-end pipeline

```
data/build_dataset.mjs  -->  data/customers.json  (24 synthetic records)
                                    |
                                    v
                        detection/detect.mjs   (rule-based, no AI)
                                    |
                                    v
                     data/flagged_customers.json  (23/24 flagged, each tagged with why)
                                    |
                                    v
                       dashboard/build.mjs   (embeds the flagged list + playbook.json into HTML)
                                    |
                                    v
                        dashboard/index.html   <-- dealer opens this, clicks a job
                                    |
                                    v  POST /diagnose
                     Worker (src/index.js): completeness_check -> Gemini/Groq -> validate
                                    |
                                    v
                     dashboard shows diagnosis, dealer Approves / Edits / Rejects
```

Regenerate top-to-bottom with:
```bash
npm run build:data        # data/build_dataset.mjs + detection/detect.mjs
npm run build:dashboard   # dashboard/build.mjs, optionally: -- --worker-url=https://your-worker.workers.dev
```

## Request/response shape

**`POST /diagnose`** — body is one raw customer record (same shape as
`test/example_records.json`, minus the `_expected_outcome` field).

Two possible shapes back, both `200`:

1. **Resolved without an LLM call** (a decision-critical field was
   missing/ambiguous):
   ```json
   {
     "ok": true,
     "llm_called": false,
     "needs_human_input": true,
     "human_question": "Was a first service appointment booked for AST-10432 at the time of delivery? (Yes / No / Unsure)",
     "record": { "...tagged record..." },
     "output": null
   }
   ```

2. **LLM diagnosis returned** (whether or not it needed review):
   ```json
   {
     "ok": true,
     "llm_called": true,
     "provider": "gemini-3.6-flash",
     "needs_human_input": false,
     "human_question": null,
     "record": { "...tagged record..." },
     "output": { "...validated RetentionAgentDiagnosisOutput..." },
     "validation_notes": []
   }
   ```
   `validation_notes` is non-empty whenever the Worker had to correct or
   flag something in the model's raw response (see below) — useful to
   surface in the dashboard for the "AI value and trust" success measure.

**`GET /health`** — no LLM call, just reports which provider keys are
configured. Useful for confirming secrets are set after deploy.

## Deploy

```bash
npm install
npx wrangler login
npx wrangler secret put GEMINI_API_KEY     # from aistudio.google.com, free
npx wrangler secret put GROQ_API_KEY       # from console.groq.com, free — fallback only
npx wrangler deploy
```

That prints your Worker URL (`https://asteron-retention-agent.<subaccount>.workers.dev`) —
that's what the GitHub Pages dashboard will call.

## Running the dashboard

1. Deploy the Worker (see above), or run `npm run dev` for a local one at `http://localhost:8787`.
2. Open `dashboard/index.html` directly in a browser (double-click it, or serve the folder with anything
   static — GitHub Pages, `npx serve`, etc.). No build step needed to view it; it's a plain static file.
3. Paste the Worker URL into the "Worker URL" field at the top (or bake a default in via
   `npm run build:dashboard -- --worker-url=https://your-worker.workers.dev` before deploying to GitHub Pages,
   so dealers don't have to type it).
4. Click "Test connection" to confirm the Worker is reachable and see which providers are configured.
5. Click a job in the queue, click **Run diagnosis**. If the record has a resolvable ambiguity, you'll get a
   dealer question first (quick-answer buttons for the two fixed questions from `completeness_check.js`, a
   free-text fallback for anything the model itself asks) — answering resubmits automatically. Otherwise you
   get the full diagnosis: category, evidence, confidence, recommended action, and a draft message to
   Approve, Edit, or Reject.

The dashboard is a **static snapshot** of whatever `flagged_customers.json` contained at build time — it
doesn't fetch live data at runtime, and "Approve" doesn't send anything real (see the footer note in the
dashboard itself). Both are deliberate demo-scope simplifications, not oversights — see "Not yet built" below
for what closing them would take.

## Local dev / testing

```bash
npm install
npm test                  # runs everything below

npm run test:local        # completeness_check.js + validate.js, no API key, no browser needed
npm run test:dashboard    # headless-DOM tests (jsdom) covering the dashboard's render + click logic

# Live: exercises the real Gemini/Groq calls
cp .dev.vars.example .dev.vars    # fill in real keys
npm run dev
curl -X POST http://localhost:8787/diagnose \
  -H "Content-Type: application/json" \
  -d @test/example_records.json    # note: this file is an array of 3 — send one record object, not the array, for a real call
```

`npm run test:local` passes 16/16 — every branch `completeness_check.js` can take on the three example
records, plus `validate.js` against hand-built good and deliberately-bad fake model responses (bad discount,
fabricated evidence, wrong playbook for the category, category D never carrying a message, a structurally
malformed response).

`npm run test:dashboard` passes 23/23 — renders all 23 flagged tickets and clicks through every one with no
exceptions, checks the missing-URL and unreachable-Worker error paths, and (in `dashboard_flow_test.mjs`)
drives the full two-step flow against a *mocked* Worker response: select a never-visited customer → get the
delivery-booking question → click "No" → get a real category-A diagnosis back → click Approve → status
updates. This caught a real bug during the build (`structuredClone` isn't available in every JS environment;
swapped for a plain JSON-round-trip clone) — worth re-running after any dashboard edit.

Neither test suite calls Gemini or Groq — this sandbox's network egress doesn't reach either API, so
`llm_client.js` is implemented per each provider's documented request/response shape but hasn't been
exercised against a live endpoint. **Do one live `wrangler dev` + dashboard smoke test with real keys before
the demo** — that's the one part of this pipeline that's untested against the real world.

## Design decisions worth defending in Q&A

**A gap the original design left open, and how it's closed.** The
literal prompt in `system_prompt.md` ends with "Output ONLY valid JSON
matching the schema you were given" — but the documented pipeline
(`reasoning-core/README.md`'s diagram) never actually attaches a schema
anywhere; it's just "system_prompt.md + tagged record → Gemini."
`system_prompt.js`'s `buildSystemInstruction()` closes that gap by
appending `output_schema.json`'s shape to the prompt at call time. Worker-side
validation remains the real safety net regardless of how well the model
follows the appended schema — this was a deliberate choice over trying
to force Gemini's native `responseSchema` parameter to fit
`output_schema.json` exactly, since that schema uses `"type": ["string","
null"]` unions that aren't valid in Gemini's OpenAPI-subset schema
format. Asking for `responseMimeType: "application/json"` plus full
code-side validation is more portable across both providers and matches
the README's own stated design: the Worker, not the model, is the
thing that's supposed to be trusted.

**The evidence-citation check is a heuristic, stated as one.**
`output_schema.json`'s fourth worker-side rule says every evidence item
must be "traceable to a field in the input record." A real citation
audit would need the model to return field-level references, which
would mean changing the schema. Instead, `validate.js` does word-overlap
matching between each evidence string and a flattened blob of the
record's own field names/values/inference-basis text — if fewer than
half of an evidence item's significant words appear anywhere in the
record, it's treated as ungrounded and `review_flag` is forced true.
This is looser than exact provenance (it will pass a well-paraphrased
citation, which is fine — paraphrase is expected) but it does catch
outright fabrication (a citation referencing something with zero
relation to anything in the record). Worth saying plainly if asked: this
is a fabrication tripwire, not a formal proof of grounding.

**Fallback provider, not fallback silence.** If Gemini fails for any
reason (quota, network, unparsable JSON), the Worker retries the exact
same prompt against Groq's llama-3.3-70b before giving up. If *both*
fail, the Worker still returns `200` with a `review_flag: true`,
`escalate_human_only` fallback record — never a bare `500` that would
leave the dashboard with nothing to show. This mirrors the same
principle README.md states for `completeness_check.js`: "the agent
asks, it doesn't guess, when it can't tell" — extended here to "the
agent doesn't drop the customer just because a provider is down."

**Belt-and-suspenders enforcement, not just prompted behavior.**
Category D (genuine quality dissatisfaction) should never carry a
customer-facing `draft_message`, per the prompt. `validate.js` enforces
this twice independently of what the model returns: once via the
`escalate_human_only → draft_message must be null` schema rule, and
again by force-setting `requires_human_review_only = true` whenever
`primary_category === "D"`, regardless of what the model said. Same
pattern the reasoning-core README already committed to for this exact
guardrail — this just makes it real in code that's actually running.

## Design decisions in the dashboard worth defending in Q&A

**Ticket/workshop visual language, not a generic admin panel.** Flagged
customers render as job tickets (monospace job numbers, a left color
bar for status, a stamp-style badge on the detail view) rather than a
generic table — grounded in the actual domain (a dealer service bay
runs on work orders and stamps, not a SaaS dashboard), and it makes
status legible at a glance across 23+ open jobs.

**The question-answering loop is real, not decorative.** When
`completeness_check.js` returns `skipLLM: true`, the dashboard doesn't
just display the question — it collects the dealer's tap (or, for a
model-originated question, free text), mutates the *working copy* of
the record (never the original flagged-list data), and automatically
resubmits to `/diagnose`. This is what makes "the agent asks, it
doesn't guess" (README.md's phrase) a live behavior in the demo instead
of a slide claim.

**Category D gets a different primary action.** Because
`requires_human_review_only` is always true for category D, the
dashboard swaps "Approve & send" (which implies a customer-facing
message exists) for "Mark reviewed by service manager" — the UI copy
matches what's actually true about the record, per the interface-copy
principle of never implying an action that didn't happen.

## Not yet built (per PROJECT_HANDOFF.md §9)

1. **Feedback loop (pipeline stage 7)** — tracking whether a customer
   actually returned after an intervention, feeding back into future
   confidence calibration. Nothing here closes that loop yet; Approve
   only updates the dashboard's own session state.
2. **Live data instead of a static snapshot.** The dashboard embeds
   `flagged_customers.json` at build time (`dashboard/build.mjs`)
   rather than fetching it at runtime — deliberate, to keep the page a
   single self-contained file with no CORS/hosting complexity for the
   demo. A production version would fetch fresh data (e.g. from a small
   API in front of the repo's JSON, or a real database) so a new
   nightly Detection run doesn't require rebuilding and redeploying the
   dashboard.
3. **Real send integration.** Approve is fully wired through the UI and
   audit log, but doesn't call an actual SMS/email/call provider — see
   the dashboard's own footer note. Stage 6 (Execution: send + log) is
   the next piece if this goes past a demo.
4. **Production hardening**: auth in front of `/diagnose` (currently
   `Access-Control-Allow-Origin: *`, wide open), rate limiting, and
   moving the discount-authorization check to pull
   `authorized_discount_range` from a trusted backend source rather
   than trusting whatever the caller's record payload says.
